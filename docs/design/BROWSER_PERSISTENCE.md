# Browser workbook persistence adaptation

Implementation sequence, updated 18 October 2026 against `65c0ae3`. **Browser workbook Save/Open remains unavailable.** The native codec now supports workspace v14; separate BP0 probes cover real v12 and owner-only v13 files, while browser C jobs now capture session registration tokens. These are distinct acceptance boundaries, detailed below. Follow the current roadmap for execution priority. Keep the shared C99/raylib UI and official asynchronous DuckDB-Wasm Worker; no new spreadsheet runtime, custom DuckDB build or JavaScript calculation model is proposed.

## Existing behavior and the missing seam

## Storage and compatibility contract

**The exported `.dxls` remains a real DuckDB database containing the native versioned metadata schema.** Browser JSON may describe a bounded transport message or an origin-local handle/index record; it is not a substitute workbook file. The current native packages are:

| Package | Metadata tables and semantics |
| --- | --- |
| Ordinary v12 | 16 tables: `meta`, `sheets`, `columns`, `cells`, `objects`, `pivot_fields`, `table_sources`, `table_filters`, `table_sorts`, `marks`, `formats`, `filters`, `sorts`, `queries`, `source_options`, `preferences`. Earlier 1–12 layouts use their existing migration/default rules. |
| Owner-only v13 | The 16 ordinary tables plus `object_counters`, `format_scopes`, `format_selectors`, `format_guards`: 20 total. Exact owner high-water marks survive deletion/reopen. Selectors are SPATIAL; scopes/guards are empty. |
| Source-aware v14 | All 20 plus `source_version_counters`, `source_versions`, `source_bindings`, `format_records`, `format_fields`, `format_state`: 26 total. `format_state` has exactly one nonnull boolean row per sheet, including `false`; mode remains independent of source counters or scope count. |

Use [`workbook.c`'s `source_tables`, `source_package_shape`, `source_model_valid` and `read_workbook`](../../src/workbook/workbook.c) as the present implementation contract. V14 validates exact known base-table names, named column sets/types, required SQL NULL rejection, embedded NUL rejection in supported VARCHAR fields, contiguous positions, complete primary/Table binding rows including version 0, owner/version high-water bounds and typed scope/record/field references. Physical column reordering is accepted through named reads/writes. Unknown tables/views in the v14 metadata schema fail. Older versions reject reserved newer source/mode metadata rather than silently losing it; ordinary v12 custom metadata behavior must not be tightened incidentally.

V14 accepts SPATIAL, RECORDS, RESULT and GUARDED selectors. RECORDS requires one canonical RAW packet; RESULT requires one canonical RESULT packet; GUARDED requires 1–33 distinct owners' canonical RESULT guards. Packets must match complete ledger RAW proofs exactly; unknown encoding, opaque blobs, dangling references, pending proofs used as guards and zero-guard GUARDED rectangles fail atomically. Pending ledger entries themselves are valid and retained. A packet is strictly below 256 KiB; ledger entries are bounded to 1,024 per sheet. The codec permits at most 512 scopes/format patches per sheet, 20,000 record members and 16,384 original-field ordinals per selector, with contiguous membership positions. Combined current format/ledger ownership is at most 1 MiB per sheet and 8 MiB per v14 archive; this newer aggregate policy does not retroactively reject ordinary v12/v13 spatial books. History and App staging reservations have separate current/retained/in-flight accounting.

The [native v14 codec](../validation/checkpoints/2026-10-18-source-format-v14/) archives proofs without verifying external files. Native App activation separately re-verifies content/schema/reader/engine and owner/definition identity; supported primary/Table RAW and archived RESULT/GUARDED activation do not imply browser verification. A browser decoder must preserve these payloads while leaving their source styles suspended. Native Save As resolves relative locators and preflights the restored representation's bounds; the browser needs an explicit logical-locator adapter, not OS `realpath` or resolution against the review server URL. Preserve externally owned data outside the metadata schema when an accepted workbook contains it; an unrecognized database must not be overwritten.

Keep three independent versions visible in evidence: Duxcel workspace schema, DuckDB file storage version and actual engine/package versions. Do not increment the workspace version merely to add a browser platform adapter. New shared persisted semantics require their own version/migration decision; preserve the accepted [source-format identity schema and remaining migration gates](SOURCE_FORMAT_IDENTITY.md#proposed-v12-migration).

Older readers are not guaranteed to open every newer engine's file. Explicit storage versions can constrain a writer, but cannot make unsupported SQL/extensions work. Therefore inspect the file through the pinned engine read-only, reject incompatible files without altering them, and prove native→browser→native on actual files. The separate v12/v13 BP0 rewrites use `STORAGE_VERSION 'v1.0.0'` successfully. Retest that target against all 26 v14 metadata tables, including canonical BLOB packets; the existing probes do not establish that compatibility. Do not rewrite the native writer's compatibility setting as an incidental browser change. [DuckDB storage contract](https://duckdb.org/docs/stable/internals/storage).

Importing a workbook must not automatically run persisted source SQL, install/load extensions, contact remote URLs or grant local file access. First validate metadata in a staging catalog, disable automatic extension installation/loading for metadata reads, and resolve source capabilities separately. Valid definitions outside accepted browser execution remain owned and preserved with an unavailable execution state; silently discarding a PIVOT/Marks definition to permit a browser save is unacceptable. Bounded Rows/Columns PIVOT, totals, statistics, Copy and Parquet export already have their own real browser acceptance; none is a workbook codec. Unknown future schema/enum values fail load atomically.

## Shared C codec and asynchronous lifetime

Extract only metadata validation, table descriptions, row encoding/decoding and version defaults into an engine-independent C99 seam. Native execution still binds typed parameters through DuckDB C; the browser executes C-built SQL through the existing Worker. Keep source-query SQL in the existing C transforms. JavaScript routes commands, file capabilities and typed results; it does not construct the workbook model, infer cell types or implement migrations.

Use ordered bounded commands/results with an operation kind, document/session cookie, monotonically increasing ticket and snapshot generation. Candidate commands are begin-open, read-metadata-batch, begin-save, write-metadata-batch, commit/checkpoint, abort and export-file. A save takes a deep `workbook_snapshot` (which can fail on invalid owned source metadata); add an explicit document mutation generation so completion clears dirty state only for that exact saved generation after durable delivery. Newer edits stay dirty. Save must not borrow mutable App strings or undo stacks while an asynchronous request is pending.

The metadata transfer contract carries explicit column descriptors and a separate null flag. UInt64/int64/DECIMAL values cross as canonical text or exact binary fields, never an unsafe JavaScript `Number`; booleans and finite presentation doubles retain their proper types. SQL NULL, an empty VARCHAR and literal `NULL` remain distinct. Sparse absent manual cells are absent records; do not manufacture empty-string cells. The current manual-cell model is text-only: persistence must preserve its current semantics, not invent typed manual editing.

Implement bounded reads and writes, initially at most 256 rows, 4 MiB of payload and 6 MiB of wire per transfer, and at most 1 MiB of C-built SQL, matching normal page/SQL ceilings. One oversized row fails explicitly; do not trim text to fit. Preserve the native per-sheet/model limits, ordered IDs/positions, UTF-8 and numeric validation; add an aggregate snapshot/transfer byte budget before offering Save. Avoid concatenating an entire 64-sheet workbook or all editable cells into one SQL string. If using C-built INSERT literals, use the existing safe SQL quoting and explicit casts for exact numeric values; do not interpolate arbitrary strings in JavaScript.

C owns snapshots, decoded rows, the candidate Workbook and final model. The host immediately copies any asynchronous command payload borrowed from the C heap; Worker buffers and browser file handles stay host-owned. Each reply is copied into C allocation before temporary host/heap allocations are released. No live pointer or DuckDB connection crosses modules. A stale callback may free its own temporary resources but cannot publish into a new document.

Extend the existing administration chain to drain/cancel source reads before a metadata operation owns the connection/catalog. Saving must not be superseded midway by viewport scrolling. Continue C input/rendering while pending; pause publication where a document replacement requires it. On failure, roll back, close temporary readers/catalogs/registrations and retain the current workbook and dirty flag. A committed save cannot be undone by ignoring its callback; define the commit boundary and account for any completed staged file during shutdown/recovery.

### Next BP1 implementation

BP1 is not a request to port the entire native SQL loader in one change. Continue the existing shared `workbook_codec` policy and opaque `workbook_codec_read` staging modules with their focused tests; the integration owner keeps App, Worker/public interfaces and build changes. Use this sequence:

1. Move the existing named table/column/type/nullability inventory and minimum-write-version policy into the shared module; make the native adapter use it without changing ordinary v1–14 behavior. Retain version-specific layouts/defaults: do not impose the v14 26-table or aggregate rules on older spatial books. Extract common model validation as needed instead of copying the v14 rules into JavaScript.
2. Add an owned decoder/cursor for bounded `meta`/`sheets` batches first, then extend one metadata family at a time until every required table and migration is covered. The cursor requests C-built, explicitly ordered named-column SQL; native DuckDB rows and browser transport feed the same row decoder. A partial family pass must not expose product Open/Save. Use schema descriptors checked before canonical projection, explicit NULL flags, exact scalar parsers and bounded hex-to-BLOB decoding for packets; ordinary source Page fallback rules are not permission to accept unknown metadata types. The native adapter still uses typed prepared bindings for writes.
3. Make asynchronous lifetime independently testable with an operation key of `(document_epoch, operation_ticket, snapshot_generation)`, all exact nonwrapping uint64 values. These are proposed operation inputs, not fields already present in Workbook. The codec owns its candidate/snapshot and cursor; the host copies each borrowed request before awaiting and carries the same key back. Late/mismatched replies clean up without publishing. Cancel before commit discards the candidate; completion after commit must retain an owned staged result until explicit delivery/cleanup. Do not reuse `analysis_revision` as the workbook generation: manual cells, object/title/format/source-ledger changes, sheet order, preferences and persisted view state also matter.

A successful decoder finish moves a fully validated candidate once; failure preserves the destination, source bytes, prior cache and dirty state. Pass an explicit locator resolver: native uses current relative-path behavior; a browser component preserves saved logical references without granting execution or rewriting them to `import-N-*`. It must load no source SQL or extensions. Snapshots omit Undo/Redo and Pages, but preserve durable owner/source high-water marks, all current definitions and inactive scopes. Project snapshot, transfer and current/staging coexistence budgets before allocating or publishing; the v14 format/ledger cap is not a whole-workbook or process-memory cap.

Keep each initial family integration behind the test boundary: C-generated metadata requests against private read-only v12/v13/v14 fixtures, decoding into the opaque partial Header with native comparisons. Only after all required families/migrations are validated may the adapter construct a complete staged Workbook. The BP0 JavaScript fixture copier is not that decoder. Add shared C-generated write batches and an actual Worker rewrite only after the read path and native regressions pass; use a fresh registered valid copy until blank creation is separately proved. Writes retain named columns, explicit exact casts/bindings and the native minimum-version decision. Accept original-file hashes and unrelated-table preservation, not only exported row counts.

Focused gates: release/ASan deep ownership and unchanged-output failures; native old fixtures and strict v14 malformed packages; split/batch-boundary and oversized-row errors; NULL/empty/literal strings; UINT64_MAX and values above2^53; exact BLOB bytes; stale operation keys; edits/Undo/new document between capture and completion; cancel/read/write/commit/export failure and recovery. The first App handoff must audit every persisted mutation before enabling generation-based dirty clearing. Until a usable output channel completes, report only a staged/export-requested result and keep dirty/recovery state. No new schema version is needed for this adapter.

## Source references and file permissions

Current session identity is already implemented: successful registration returns canonical nonzero uint64 `engineEpoch`/`registrationId` strings; App captures POD tokens for up to 33 unique declared primary/Copy/Statistics file paths. Every SQL stage, including schema/domain/totals and export, carries the frozen vector; schema/type caches require the same exact names/order/tokens. The official adapter validates before admission/send and after completion. The [actual App680 and Worker221 gates](../validation/checkpoints/2026-10-18-session-source-bindings/) include cached contributors, revocation, malformed vectors and atomic budget denial/recovery. Unbound low-level callers retain their explicit legacy contract; missing required App bindings fail closed.

This protects registered immutable buffers sharing one database object during one session only. It does not infer undeclared custom-SQL/remote dependencies, detect raw database/file writes outside that API, unify separate wrappers around an engine, hash content or survive engine replacement/reload. Names/IDs are permanently burned within the bounded 1,024-name registry. Friendly original filenames are session UI labels, separate from executable keys and identity. None of these tokens or labels may be promoted into native `Analysis.source_version`/SourceVersions proofs or serialized as cross-session authority.

Keep a persisted logical source reference separate from its current engine registration. The current `Analysis.path` is used to build SQL; introduce a narrow resolver/binding seam so browser runtime aliases do not replace the saved reference. The future persistent binding includes the snapshot's sheet/object owner, source kind/reference, reader options and expected schema/version hints; it is separate from the accepted runtime token vector. Sheet reorder/duplication/save must rebuild the owner mapping for the new generation; table/object owners cannot share a binding merely because basenames match.

For Chromium-capable hosts, acquire `showOpenFilePicker`/`showSaveFilePicker` handles directly during the originating trusted gesture, before asynchronous snapshot/engine work. Store permitted handles in a separate origin-local IndexedDB directory keyed to the committed document generation; check permissions on resume and request permission only on an explicit user action. The existing raylib frame dispatch can occur after the DOM event's transient activation, so the platform adapter must prove gesture handoff rather than assume a later frame can open a picker. Retain `<input type=file>` and download fallbacks. [Chrome file/gesture/handle contract](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

Reload should restore definitions immediately and show unresolved sources without prompting. Resolve a remembered handle only if permission and expected source checks pass; otherwise expose the shared C Relink action. Canceling a picker changes nothing. Relinking affects only the intended owner and invalidates its schema/pages/query generations before execution. Match source kind and schema; size/mtime/name are hints, not a verified content identity. Source-record styles requiring verified provenance stay suspended until their own identity contract passes.

Prefer registering a selected `File` through the pinned official `BROWSER_FILEREADER` handle path for bounded random access, once measured and accepted, rather than unconditionally cloning a 256 MiB source. This is a separate improvement to the existing buffer importer. No implicit copy of external data into OPFS occurs: offer an explicit retained-source copy only with quota, progress, cancellation and identity checks. Large-file import caps stay honest until streaming/handle paths pass. [Official file registration API](https://duckdb.org/docs/clients/wasm/data_ingestion).

## Save, recovery and portable export

First deliver explicit import/export through a private staging database. Validate imported bytes and metadata before swapping the current document; write metadata transactionally, then checkpoint/flush and copy through an accepted official API sequence for bounded `.dxls` download or a user-granted writable stream. Never export a file while it still depends on an unexported WAL. A download request is not proof of a completed durable save, and must not clear the only dirty/recovery copy. In a file-handle path, report success only after the write stream closes successfully.

The accepted BP0 path has two separate modes: [v12 / 16 tables](../validation/checkpoints/2026-10-17-browser-platform/) and [owner-only v13 / 20 tables](../validation/checkpoints/2026-10-18-sql-review-owner-lifetimes/) with exact high-water sentinels above 2^53 / at UINT64_MAX / zero. It registers a separately owned **valid native database buffer**, drops/recreates only its fixture metadata schema from engine-described DDL, commits, checkpoints, flushes and copies bytes while the private writer is quiescent, then detaches. Native loading verifies the resulting file. This is a Save-As foundation, not accepted blank-document creation: an unregistered newly created file failed `copyFileToBuffer` both before and after detach; an empty registered buffer failed `ATTACH`; the pinned `registerEmptyFileBuffer` implementation is a no-op. Establish a working blank-file/handle adapter before offering New→Save. Do not infer method behavior from declarations. Catalog nullability is projected as canonical `VARCHAR`; direct Arrow boolean catalog getters produced invalid values in this probe. Shared source pages already use C-built canonical projections. The cloned fixture export grows, so compaction/storage cost and preservation of unrelated user tables need their own gates. No actual v14 BP0 round-trip or shared C browser codec is claimed. Accepted typed Parquet COPY/download uses a different file format and does not resolve blank DuckDB workbook creation.

An exported workbook retains source references, as native does; external CSV/Parquet files are not automatically embedded. Preserve usable native relative references when importing and re-exporting a native workbook. For browser-selected files without a directory capability, save a logical reference and require relink after moving to native. A `.dxls` that opens with missing sources is different from a self-contained data package. Do not promise the latter in this milestone.

Then add origin-local recovery under one stable, product-specific namespace, separate from review IndexedDB/outbox/service state. Use the official Worker's OPFS path and explicit manual file registration where verified; no synchronous filesystem work belongs on the UI thread. The official guidance requires checkpointing and releasing exclusive handles before another engine opens a file. Exercise the exact pinned implementation rather than treating current documentation as a pass. [Official OPFS lifecycle](https://duckdb.org/2026/09/18/opfs-wasm).

Persist generations: write a new staging generation, commit/checkpoint/close it, verify reopening, then atomically advance a small IndexedDB committed-generation pointer. Keep the previous good generation until the pointer commit is confirmed. OPFS and IndexedDB do not share a transaction; after a crash, an unreferenced staging file is an orphan, not the newest accepted workbook. On recovery, validate the pointer and file, fall back to the prior committed generation on corruption, and offer explicit recovery without discarding the current document. Prune only owned inactive generations after successful commits.

Allow a single writer per document/origin using a feature-detected cross-tab lock plus the OPFS engine's real exclusivity. A second tab must offer read-only/open-a-copy behavior or an explicit busy result; it must not write concurrently or steal a live engine's handle. Close/detach/drop in order on document change, Worker termination and page lifecycle. Do not depend on `beforeunload` to finish an asynchronous save.

Estimate storage before staging large writes and handle quota failures at every actual write/flush/commit. Retain the old pointer/generation and unsaved C snapshot on rejection. Persistent-storage requests may be declined, estimates are not reservations, and origin data can still be removed by the user. Surface recovery-only versus externally exported state through the existing C document/status controls, without redesigning the reference UI. Changing scheme/host/port creates a different storage scope; the review service is never required for product workbook persistence. [Storage persistence/quota model](https://storage.spec.whatwg.org/).
