You are acting as the founding engineer, systems architect,

Your assignment is to build a real, usable, cross-platform

Inspect the repository before making changes.

Preserve working functionality where sensible, but you may

------------------------------------------------------------
1. PRODUCT VISION
------------------------------------------------------------

Duxcel is an analytical spreadsheet application.

Its central idea is:

    Excel's tactile spreadsheet experience
    +
    DuckDB's analytical capabilities
    +
    Reproducible visual data transformations

The application should make exploring and manipulating
large datasets feel as immediate and natural as working
in Microsoft Excel.

However, Duxcel is NOT intended to be an Excel clone.

It is a SQL-native, data-first desktop application with
a spreadsheet-inspired interaction model.

The primary use case is exploratory data analysis.

A typical user should be able to:

1. Open a CSV or Parquet file.
2. Immediately see the data in a familiar grid.
3. Scroll through millions of rows efficiently.
4. Select cells, ranges, rows, and columns.
5. Inspect data types.
6. Sort and filter columns visually.
7. Transform columns without manually writing SQL.
8. Perform aggregations and pivots.
9. Create visualizations associated with worksheets.
10. Inspect the SQL generated by those interactions.
11. Save the analytical workspace.
12. Reopen the workspace and reproduce the analysis.

The user should not need to interact with a notebook,
write Python, or manually construct SQL for everyday
exploratory operations.

SQL must remain available as an escape hatch.

The application should prioritize:

- Responsiveness
- Direct manipulation
- Low interaction latency
- Data visibility
- Reproducibility
- Simplicity
- Large dataset support
- Cross-platform behavior

Think of Duxcel as an interactive analytical workspace,
not a traditional spreadsheet for accounting or data entry.

3. FUNDAMENTAL ARCHITECTURAL PRINCIPLE
------------------------------------------------------------

Every analytical worksheet represents a DuckDB relation
or a SQL query defining a relation.

The spreadsheet grid is a visualization and interaction
surface over that relation.

Do not model the entire dataset as an enormous
two-dimensional C array.

The underlying dataset may contain tens or hundreds
of millions of rows.

Only the visible data and a bounded surrounding cache
should be materialized for presentation.

The database remains the source of truth.

The UI should never need to load the entire relation
into memory merely to display or navigate it.

Logical architecture:

    Data Sources
        |
        v
    DuckDB
        |
        v
    Query / Transformation Engine
        |
        v
    Worksheet Model
        |
        v
    Virtualized Grid
        |
        v
    raylib Renderer

The renderer must not know how SQL queries are executed.

The database layer must not know how cells are drawn.

The workbook must not be tightly coupled to raylib.

Keep the architecture modular but avoid unnecessary
enterprise-style abstractions.

5. HIGH-DPI AND CROSS-PLATFORM UI
------------------------------------------------------------

Duxcel must handle normal and high-density displays.

This has already been an issue during initial raylib
experimentation on macOS Retina displays.

Use:

    SetConfigFlags(FLAG_WINDOW_HIGHDPI);

before creating the window.

However, do not assume all displays have the same DPI.

Distinguish between:

1. Logical window coordinates
2. Physical framebuffer pixels
3. User-configurable UI scaling
4. Font rasterization resolution

These concepts must not be conflated.

The application should have a centralized UI context.

Example:

    typedef struct {
        float user_scale;
        Vector2 dpi_scale;
        float base_font_size;
        float row_height;
        float column_width;
        float padding;
    } UIContext;

The exact implementation is your responsibility.

Requirements:

- Query DPI using raylib's APIs.
- Avoid double-applying DPI scaling.
- Handle window resizing.
- Support UI scaling independent of display DPI.
- Recalculate layout when UI scale changes.
- Handle display DPI changes where supported.
- Avoid blurry text on Retina displays.
- Keep mouse hit-testing consistent with rendering.
- Keep scrolling and selection coordinates correct.

The application must have a single coherent
coordinate-system policy.

Document it.

Do not scatter DPI multiplication throughout
individual widgets.

    Select current data region or all visible relation

25. IMPORTANT PRODUCT PHILOSOPHY
------------------------------------------------------------

The most important feature is not SQL execution.

DuckDB already executes SQL extremely well.

The product's value is making analytical operations
feel immediate, visual, and intuitive.

Optimize for an analyst who wants to touch the data.

The user should be able to explore first and
understand the generated SQL afterward.

Prefer:

    Select column
    -> Filter
    -> Inspect data
    -> Group
    -> Aggregate
    -> Visualize

over:

    Open SQL editor
    -> Write query
    -> Execute
    -> Inspect result
    -> Rewrite query

Do not sacrifice this philosophy simply because
a SQL editor would be easier to implement.

At the same time, do not sacrifice correctness
or performance to imitate spreadsheet behavior.

The final product should be an analytical instrument,
not a spreadsheet costume over a database.
